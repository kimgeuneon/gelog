## 핵심 결론

Policy server를 **여러 대 띄우고 gRPC + Protobuf로 서빙**하며, 앞단에서 **로드밸런싱**하는 구조가 가장 적합합니다.

## 1. 상황

- Policy server를 띄워두고 **여러 곳에서 동시에** 요청을 보냅니다.
- 요청 주체는 프로세스, 디바이스(로봇 등)입니다.
- **프로세스 간 통신**과 **디바이스별 통신**이 가장 먼저 수요가 높습니다. 서빙을 먼저 익혀야 하는 이유입니다.

## 2. 방식별 판단

| | 평가 | 이유 |
|---|---|---|
| **gRPC** ✅ | 서비스용으로 채택 | 서버 여러 대 + 로드밸런싱에 적합합니다. Protobuf라 직렬화가 빠르고, 타입 계약으로 클라이언트 코드가 자동 생성됩니다. |
| **WebSocket** △ | 프로토타입용 | 구현이 간단합니다. 하지만 영속된(stateful) 연결이라 여러 서버로 분산하기 어렵습니다. |
| **GraphQL** ✗ | 이 케이스엔 불필요 | 클라이언트가 필요한 필드를 골라 조회하는 기술이라 모델 추론 서빙과 맞지 않습니다. |

## 3. 왜 JSON이 아니라 Protobuf인가

- JSON은 텍스트라 크고, 직렬화/역직렬화 비용이 큽니다.
- Protobuf는 바이너리라 작고 빠릅니다. 스키마(`.proto`)가 있어 타입이 보장됩니다.
- VLA 서빙도 처음부터 Protobuf로 하는 편이 낫습니다. 이미지/관측 데이터를 계속 주고받는 구조라 효과가 큽니다.

## 4. 개념으로 이해하기

- WebSocket은 한 서버와 **연결을 유지**하는 방식입니다. 연결이 특정 서버에 붙으니 서버를 늘려도 분산이 어렵습니다.
- gRPC는 **요청 단위**로 서버를 고를 수 있어서, 서버를 늘리고 로드밸런서로 요청을 나눌 수 있습니다.

```
[클라이언트 A/B/C...]  →  [로드밸런서]  →  [Policy Server 1]
   (프로세스·디바이스)                    →  [Policy Server 2]
        gRPC + Protobuf                    →  [Policy Server N]
```

## 5. 실무에서 걸릴 만한 점

1. **로드밸런싱 방식**: gRPC는 HTTP/2 연결을 오래 유지합니다. 단순 L4 로드밸런서를 쓰면 한 연결이 한 서버에 계속 붙어서 분산이 안 될 수 있습니다. L7 프록시(Envoy 등)나 클라이언트 측 로드밸런싱이 필요합니다.
2. **메시지 크기**: gRPC 기본 최대 수신 크기는 4MB입니다. 고해상도 이미지를 여러 장 보내면 한도를 올려야 합니다.
3. **병목 위치**: VLA는 보통 모델 추론 시간이 통신 시간보다 훨씬 큽니다. Protobuf의 이득은 이미지 같은 큰 텐서를 `bytes` 필드로 효율적으로 보낼 때 가장 큽니다. 실제 지연은 측정해 보세요.
4. **스트리밍**: 연속 제어 루프에는 양방향 스트리밍이 맞을 수 있습니다. 요청마다 하나씩 보내는 Unary와 비교해 보세요.
5. **디바이스 환경**: 디바이스(로봇)에서 gRPC 클라이언트를 쓸 수 있는지 언어와 OS 지원을 먼저 확인하세요.

## 6. 표현 정정

- "WebSocket은 서비스로는 쓰지 못한다"는 과장입니다. 채팅이나 실시간 서비스에서 실제로 많이 씁니다. 정확히는 **"여러 대 분산 서빙이 필요한 policy 서빙에는 gRPC가 더 적합하다"** 입니다.
- GraphQL은 API 쿼리 언어입니다. 크롤링에서는 대상 사이트가 GraphQL API를 쓸 때 그 요청을 직접 호출하면 효율적이라는 정도입니다.

## 7. 학습 순서

1. 프로세스 간 통신: gRPC 서버와 클라이언트 만들기 (Python 기준 `.proto` → 코드 생성)
2. 디바이스별 통신: 여러 클라이언트가 동시에 접속하는 상황 만들기
3. 서버 여러 대와 로드밸런싱: 분산이 실제로 되는지 확인
4. JSON과 Protobuf 지연/크기 비교: 직접 측정

## 부록: gRPC · GraphQL · WebSocket 개요

| | gRPC | GraphQL | WebSocket |
|---|---|---|---|
| 정체 | RPC 프레임워크 | 쿼리 언어 + 런타임 | 전송 프로토콜 |
| 전송 | HTTP/2 | 주로 HTTP (구독은 WS) | TCP (HTTP 업그레이드) |
| 데이터 | Protobuf (바이너리) | JSON | 자유 (텍스트/바이너리) |
| 방향 | 단방향 + 스트리밍 4종 | 요청/응답 (+구독) | 양방향 |
| 브라우저 | 프록시 필요 | 바로 가능 | 바로 가능 |
| 강점 | 속도, 타입 계약 | 유연한 조회 | 실시간 |
| 약점 | 디버깅, 브라우저 | 캐싱, N+1 | 확장성, 상태 관리 |

- **gRPC**: `.proto`에 서비스와 메시지를 정의하면 코드가 자동 생성됩니다. 통신은 Unary, Server streaming, Client streaming, Bidirectional streaming 4가지입니다.
- **GraphQL**: 단일 엔드포인트에서 필요한 필드만 골라 요청합니다. N+1 문제는 DataLoader로 배치 처리하고, 악성 쿼리는 depth/complexity 제한으로 막습니다.
- **WebSocket**: HTTP Upgrade 핸드셰이크 후 하나의 TCP 연결에서 양방향 통신을 합니다. 서버 확장에는 메시지 브로커(Redis 등)가 필요합니다. 서버→클라이언트 단방향만 필요하면 SSE가 더 단순합니다.
