## 왜 만들었나

맥에서 Negotium으로 에이전트와 대화를 하다가 집을 나서면, 그 대화는 맥 앞에 돌아올 때까지 멈춘다. 에이전트가 긴 작업을 하는 중이라면 더 답답하다. 지금 어디까지 했는지 볼 수 없고, 방향이 틀렸다는 걸 알아도 멈추게 할 방법이 없다.

Negotium은 맥을 "에이전트 노드"로 만드는 CLI 도구다. 터미널, 텔레그램 같은 여러 화면(어댑터)이 노드 하나를 공유하고, 대화 기록과 AI 실행은 모두 노드가 가진다. 그렇다면 폰도 어댑터 하나가 될 수 있지 않을까. 외출 중에도 폰으로 맥에서 하던 세션에 이어서 말을 걸고, 진행 상황을 보고, 필요하면 멈추게 하고 싶었다. 그게 이 프로젝트의 전부다.

## 노드가 이미 열어 둔 문

먼저 노드가 밖에서 조종할 수 있는 상태인지 확인했다. 노드는 `127.0.0.1`에 HTTP 서버를 열고 있었고, Bearer 토큰으로 인증하는 REST + SSE API가 있었다. 공식 문서를 찾기보다 번들된 소스를 읽어서 엔드포인트를 파악했다.

| 하는 일 | 엔드포인트 |
|---|---|
| 토픽 조회 | `GET /topics/{id}` |
| 메시지 기록 | `GET /topics/{id}/messages` |
| 메시지 전송 | `POST /turns` |
| 실시간 이벤트 | `GET /events` (SSE) |
| 진행 중단 | `POST /topics/{id}/abort` |
| 에이전트 질문에 답하기 | `POST .../ask-answer` |

필요한 것은 다 있었다. 보기, 보내기, 멈추기, 실시간으로 받기. 남은 일은 이 API를 폰에서 안전하게 부르는 통로를 만드는 것이었다.

## 안드로이드 앱 대신 PWA

처음에는 Kotlin으로 안드로이드 앱을 만들까 했다. 그런데 혼자 쓸 물건에 SDK 설치, 빌드, 수정할 때마다 APK 재설치를 반복하는 비용이 너무 컸다.

그래서 PWA로 갔다. 화면은 순수 JS로 만들고, 수정하면 새로고침으로 바로 반영된다. "홈 화면에 추가"를 하면 아이콘도 생기고 앱처럼 열린다. 혼자 쓰는 도구라면 이 정도면 충분했다.

## 구조: 폰과 노드 사이에 브리지 하나

```
[폰 (PWA, 순수 JS)]
        │  https + access key
        ▼
[Cloudflare Tunnel]
        │
        ▼
[Bun 브리지 서버]  ── 약 100줄, 의존성 없음, 127.0.0.1에만 바인딩
        │  노드 토큰 (브리지만 읽는다)
        ▼
[Negotium 노드]  ── 127.0.0.1, REST + SSE
```

핵심은 노드 토큰을 폰에 두지 않는 것이다. 노드 토큰은 브리지만 읽고, 폰에는 별도의 access key만 둔다. 폰은 access key로 브리지에 요청하고, 브리지가 노드 토큰을 붙여서 노드에 전달한다. 브리지는 Bun으로 약 100줄, 외부 의존성 없이 썼다.

## 부딪힌 문제 세 가지

### 토픽 목록이 빈 배열

첫 화면에 토픽 목록을 띄우려고 API를 불렀더니 빈 배열이 돌아왔다. 분명 터미널에서 대화 중인 토픽이 있는데도 그랬다.

이유는 API가 목록으로 주는 토픽이 otium 표면의 토픽뿐이라는 것이었다. 터미널에서 만든 토픽은 ID를 알면 조회할 수 있지만 목록에는 나오지 않았다. 그래서 브리지가 `negotium topics` 명령의 출력을 파싱해서 목록을 구성하도록 했다. 우아하지는 않지만 CLI 출력이 곧 진실이니 이쪽이 확실했다.

### SSE를 열자마자 과거가 쏟아진다

실시간 진행 상황을 보려고 `GET /events`를 열었더니, 연결하자마자 지금까지의 이벤트가 전부 재생됐다. `after` 커서 없이 열면 처음부터 다시 보내 주는 구조였다.

폰에서 커서를 관리하게 하면 복잡해지니, 브리지가 현재 커서를 먼저 조회해서 `after`로 넣어 SSE를 열도록 했다. 폰은 연결한 시점 이후의 이벤트만 받는다.

### 밖에서 어떻게 들어오나

집 맥은 공인 IP도 없고 포트 포워딩도 하고 싶지 않았다. `cloudflared`의 임시 터널을 썼다. 명령 하나로 `https://<your-tunnel>.trycloudflare.com` 같은 주소가 생기고, 그 주소로 들어온 요청이 맥의 브리지로 전달된다.

브리지 자체는 `127.0.0.1`에만 바인딩했다. 터널을 거치지 않고는 같은 네트워크에서도 브리지에 닿을 수 없다.

한 가지 짚고 넘어간 것이 있다. 회사 네트워크에서 포트를 열거나 터널을 쓰는 것은 보안 정책 확인이 필요한 일이다. 이 글의 구성은 개인 장비와 개인 네트워크를 전제로 했다.

## 한 노드를 여럿이 쓰지 않기로 한 이유와 바뀐 구조

여기까지 만들고 나니 "다른 사람도 쓰게 하면 어떨까"라는 생각이 들었다. 가장 쉬운 방법은 내 노드를 여러 사람이 공유하는 것이다. 그런데 이건 금방 접었다.

에이전트는 호스트에서 명령을 실행한다. 노드를 공유한다는 것은 그 맥의 셸을 내주는 것과 같다. 토픽 ID만 알면 남의 세션에 접근할 수 있고, 파일을 읽고 쓰는 것도 막을 수 없다. 서버를 통째로 내주는 셈이다.

그래서 "사용자별 노드" 모델을 선택했다. 각자 자기 맥에서 노드와 브리지를 돌리고, 웹앱은 공용으로 한 번만 배포한다.

바뀐 구조는 이렇다.

1. 정적 웹앱을 한 번 배포한다.
2. 각자 자기 맥에서 `start.sh`로 브리지와 터널을 실행한다.
3. 로그인 화면에서 자기 브리지 주소와 access key를 입력한다.

이를 위해 브리지에 Bearer 인증과 CORS를 추가했다. 웹앱과 브리지가 다른 출처에 있으니 CORS가 필요했고, 요청마다 `Authorization: Bearer <your-key>`를 붙인다.

여기서 하나 더 바꾼 것이 있다. 처음에는 SSE를 `EventSource`로 받았는데, `EventSource`는 요청 헤더를 붙일 수 없어서 Bearer 인증과 함께 쓸 수 없다. 그래서 `fetch`로 스트림을 열고 SSE 형식을 직접 파싱했다.

```js
const res = await fetch(`${bridge}/events`, {
  headers: { Authorization: `Bearer ${key}` },
});
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buf = '';
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += decoder.decode(value, { stream: true });
  // 빈 줄이 이벤트 경계다
  let i;
  while ((i = buf.indexOf('\n\n')) >= 0) {
    handleEvent(buf.slice(0, i));
    buf = buf.slice(i + 2);
  }
}
```

## 다중 사용자 확장 계획

이 섹션은 아직 구현하지 않은 계획이다. 일정이나 성과를 단정하지 않고, 검토 중인 내용을 적는다.

**기본 원칙은 사용자별 노드다.** 정적 웹앱을 한 번 배포하고, 사용자는 자기 브리지 주소와 키를 입력한다. 이 구조까지는 구현했다. 사용자가 자기 서버를 운영하므로 개인 정보와 비용을 운영자가 떠안지 않는다는 장점이 있다.

**다음 단계로 검토 중인 것:**

- Cloudflare 정식 터널로 주소 고정
- 주소와 키를 QR 코드로 전달
- launchd로 부팅 시 자동 실행
- 앱에서 여러 노드 저장·전환
- Web Push 알림 (서비스 워커 + VAPID)
- 파일·이미지 첨부
- 토픽 생성, 모델 변경 UI

**중앙 서비스로 노드를 공유하는 안은 현재 선택하지 않았다.** 이유는 앞에서 적은 그대로다. 에이전트가 호스트에서 명령을 실행하므로, 노드를 공유하는 순간 토픽 ID만 알아도 남의 세션에 접근할 수 있고 호스트의 파일과 셸이 열린다. 이걸 막으려면 아래 것들이 전부 필요하다.

| 영역 | 필요한 것 |
|---|---|
| 계정·세션 | 이메일/OAuth 로그인, 서버 세션, 초대 가입, 로그인 시도 제한 |
| DB | SQLite로 시작, 커지면 PostgreSQL. `users`, `sessions`, `node_topics`(토픽 소유 매핑), `audit_log`, `usage_counters`, `invites` |
| 핵심 규칙 | 모든 토픽 요청에서 소유자 검사. 없으면 토픽 ID만 알아도 남의 세션에 접근된다 |
| 한도 | 사용량 한도, 동시 실행 제한, 비싼 모델은 역할별 허용 |
| 격리 | 에이전트 실행 환경 격리 (컨테이너, 별도 OS 계정, 파일 접근 범위 제한) |
| 운영 | 자동 재시작, 백업(DB + 노드 상태 디렉터리), 로그·모니터링, 비밀 값은 환경변수 |
| 법적 확인 | 대화 저장 시 개인정보 고지와 보관 기간, AI 제공사 약관(계정 공유·재판매 제한) |

**로드맵은 이렇게 잡아 두었다.** 1단계는 정식 터널, 자동 실행, QR 연결. 2단계는 다중 노드 전환, 푸시, 첨부. 3단계는 필요해지면 계정, 소유 검사, 사용량 한도, 관리자 화면. 4단계는 규모가 커지면 PostgreSQL, 컨테이너 격리, 작업 큐. 3단계 이후는 실제로 여러 사람이 쓰게 될 때 다시 판단할 예정이다.

## 한계와 주의

- 임시 터널 주소는 재시작마다 바뀐다. 고정하려면 정식 터널이 필요하다.
- access key는 그 맥의 에이전트를 조종하는 열쇠다. 공유하면 안 된다.
- 에이전트의 질문(ask)에 선택지로 답하는 UI는 메시지 형식을 추측해서 만들었다. 실제 동작은 검증하지 못했다.
- 메시지 전송과 브라우저 화면 동작 중 직접 끝까지 검증하지 못한 부분이 있다.
- 회사 장비나 사내망이면 보안 정책 확인이 먼저다.

## 배운 점과 다음에 할 일

**배운 점**

1. **토큰을 어디에 둘지가 구조를 정한다.** 노드 토큰을 폰에 두지 않기로 한 순간 브리지가 필요해졌고, 브리지가 있으니 인증과 CORS와 SSE 파싱이 따라왔다. 비밀 값의 위치를 먼저 정하면 나머지 구조는 거의 저절로 나온다.
2. **API 목록이 비어 있어도 CLI는 알고 있다.** 목록 API가 일부 토픽만 주는 상황에서, 번들 소스와 CLI 출력이 더 확실한 정보원이었다. 문서보다 실제 동작을 먼저 보는 습관이 시간을 아꼈다.
3. **"여럿이 쓰게 하자"는 생각은 보안 질문으로 먼저 바꿔야 한다.** 에이전트가 호스트에서 명령을 실행한다는 사실 하나가 공유 모델을 통째로 기각했다. 편의 기능을 더하기 전에 그 기능이 누구에게 어떤 권한을 주는지부터 따지는 게 맞았다.

**다음에 할 일**

- 임시 터널을 Cloudflare 정식 터널로 바꿔 주소를 고정할 예정이다.
- `start.sh`를 launchd에 등록해 맥을 켜면 브리지와 터널이 자동으로 뜨게 할 예정이다.
- 브리지 주소와 키를 QR 코드로 넘기는 연결 흐름을 검토 중이다.
- 추측으로 만든 질문(ask) 선택지 UI를 실제 메시지로 검증할 예정이다.
