## 결론

**바깥(사람, 서버, 원격 GPU 박스)은 HTTP 계열로, 레인 안쪽(평가기, 센서, 정책)은 WebSocket과 ZeroMQ로 나눠서 연결한다.** 구간마다 "누가 누구와, 얼마나 자주, 어떤 데이터를 주고받는가"가 달라서 한 가지 방식으로 통일하지 않고 그 성격에 맞는 방식을 골랐다.

![하네스 통신 구조: 대시보드, sessionfront, runman, 에이전트, 레인 박스 안의 노드들, VLA 정책 서버](../../assets/diagrams/harness.svg)

| 구간 | 선택한 방식 | 핵심 이유 |
|---|---|---|
| 대시보드 → sessionfront | HTTP + SSE | 요청은 HTTP로 충분하고, 진행 상황은 서버에서 브라우저로 흐르는 단방향 스트림 |
| sessionfront → runman | HTTP (즉시 202) | 레인 부팅에 약 270초가 걸려서 응답을 붙잡아 둘 수 없음 |
| runman → 레인 박스 | SSH 터널 | 레인이 원격 GPU 박스에 있어서 이미 쓰는 SSH로 포트를 끌어오면 됨 |
| 에이전트 ↔ teleop | MCP (HTTP) | 에이전트가 도구를 부르는 표준 방식 |
| 에이전트 ↔ dataset | MCP (stdio) | 같은 머신의 보조 프로세스라 포트가 필요 없음 |
| 평가기 ↔ teleop | WebSocket + msgpack | 공식 평가기가 정해 둔 프로토콜 |
| teleop ↔ 센서 노드 | ZeroMQ (ipc) | 같은 호스트라서 마운트만으로 연결, 데이터 성격별 패턴 선택 |
| teleop ↔ VLA 서버 | WebSocket | 상시 켜 둔 서버에 연결을 유지하며 반복 호출 |

## 1. 에이전트와 도구는 MCP로 통일했다

**에이전트와 도구 사이는 전부 MCP로 연결한다.** 왜냐하면 에이전트 쪽이 하나가 아니기 때문이다.

- LLM 백엔드가 Codex, Claude, 자체 하네스(Switchboard) 세 가지다. 도구를 MCP로 내놓으면 어떤 에이전트가 와도 도구 코드를 바꾸지 않는다.
- 내비 도구도 같은 teleop MCP 서버 안에 있어서, 내비용 MCP를 따로 붙일 필요가 없다.
- 대화형 하네스와 제출용 eval 서버가 같은 teleop 도구 코드를 쓴다. 통신 방식이 같아서 가능한 일이다.
- 도구 한 번이 오래 걸릴 수 있어서 타임아웃을 420초로 넉넉히 잡았다.

## 2. 평가기와는 WebSocket + msgpack이다

**평가기와는 공식 프로토콜(upstream v3.9.3) 그대로 WebSocket + msgpack으로 붙는다.** 이건 고른 것이 아니라 맞춘 것이다.

- 공식 평가기가 정책 서버에 WebSocket 클라이언트로 접속하는 구조다. 평가기를 고치지 않으려면 우리가 그 자리의 서버가 되어야 한다.
- 그 서버가 teleop이다. 다만 teleop은 스스로 행동을 내지 않고 **에이전트가 시킨 행동만 전달하는 relay policy**다. 정책 역할은 에이전트가 맡는다.
- msgpack은 이미지나 배열 같은 바이너리를 JSON보다 작고 빠르게 실어 나른다.

## 3. 레인 안의 노드끼리는 ZeroMQ(ipc)다

**teleop과 로컬라이제이션, 디텍션, 포즈 노드는 ZeroMQ ipc 소켓으로 묶는다.** 왜냐하면 전부 같은 호스트의 컨테이너이기 때문이다.

- 호스트의 `/tmp/runman-<run_id>-channels` 디렉터리를 컨테이너의 `/channels`에 마운트하면 끝이다. 네트워크 포트를 따로 열 필요가 없다.
- 데이터 성격에 맞춰 패턴을 달리 골랐다.

| 데이터 | 패턴 | 이유 |
|---|---|---|
| pose, obstacles, detections | PUB/SUB, 최신 값만 유지 | 옛 값은 의미가 없고 항상 최신 값만 필요하다 |
| frames, images | PUB/SUB | 센서 데이터를 계속 흘려 보내기만 하면 된다 |
| odometry | PUSH/PULL | 한 방향으로 빠짐없이 전달한다 |
| calls (pose 추정 요청) | REQ/REP | 요청을 보내고 결과를 받아야 한다 |

## 4. 원격 레인은 SSH 터널로 접근한다

**runman은 SSH 터널로 레인의 제어 포트를 로컬로 끌어온다.** 왜냐하면 레인이 원격 GPU 박스에 있기 때문이다.

- runman은 이미 SSH로 박스에 붙어서 컨테이너를 띄운다. 같은 SSH로 포트를 끌어오면 별도로 포트를 열거나 인증을 만들 필요가 없다.
- 제어 포트는 로컬의 임의 포트로 끌어오고, rewind 레인이면 `8700+gpu`도 함께 끌어온다.

## 5. 오래 걸리는 일은 즉시 응답하고 비동기로 이어간다

**부팅과 턴 실행은 요청을 받자마자 202를 돌려주고, 진행 상황은 따로 알려준다.** 왜냐하면 둘 다 요청 하나가 끝날 때까지 기다리기엔 너무 길기 때문이다.

- 레인 요청(`POST /runs`)은 바로 `202 booting`이 돌아오고 부팅에 약 270초 걸린다. 빈 GPU가 없으면 503이다.
- 턴 전송(`POST .../turns`)도 202이고, 턴이 이미 돌고 있거나 세션이 끝났으면 409다.
- 진행 상황은 SSE로 브라우저에 흘려 보낸다. 에피소드 종료는 sessionfront가 5초마다 결과를 확인해서 세션을 `finished`로 바꾼다.

## 6. 레인 포트는 규칙으로 고정했다

**레인 번호 N만 알면 모든 포트가 계산되도록 규칙을 정했다.**

- `8000+N`: 평가기 ↔ teleop WebSocket
- `8000+N+300`: teleop 제어 API와 `/mcp`. +100이 아닌 이유는 8100을 datahub가 쓰고 있어서다.
- `8700+gpu`: rewind shim (rewind 레인만)

레인이 여러 개 떠도 포트가 겹치지 않고, 어느 레인에 접속할지 바로 알 수 있다.
